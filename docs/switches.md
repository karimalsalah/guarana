# Switch registry

Every `EDEN_NX2_*` switch that Guarana adds, or relies on, with what it does, its status and what it measured. Upstream Lichii has about 170 more; they are in [AGENTS.md](../AGENTS.md) ("Debugging tools"), [nx2/debug-mcp.md](nx2/debug-mcp.md) and [dist/nx2_switches.txt](../dist/nx2_switches.txt), and are listed here only when we rely on them.

A pull request that adds, changes or removes a switch updates its row here. The tree is the source of truth for names and values: `grep -rn "EDEN_NX2_" src`. CI checks this: `python3 -I tools/ci/switch_registry.py` fails on an `EDEN_NX2_*` or `EDEN_DKB_*` name used in `src/` or `launcher/` that has no row here (a table line whose first cell names it) and is not one of upstream's (in the `upstream` branch or [tools/ci/switch-registry-upstream.txt](../tools/ci/switch-registry-upstream.txt)), and warns about rows whose switch is used nowhere.

## Setting a switch

- As an environment variable before the emulator starts: `set EDEN_NX2_GM=11` in `cmd`, `$env:EDEN_NX2_GM = "11"` in PowerShell, `EDEN_NX2_GM=11 ./guarana` on Linux.
- Or as a `NAME=VALUE` line in `nx2_switches.txt`, which the GUI reads at start: the copy next to the executable, then your own in `%APPDATA%\guarana\nx2_switches.txt` (or `$XDG_CONFIG_HOME/guarana/nx2_switches.txt`), which wins. A variable in the real environment wins over both. A file next to the executable may set only `EDEN_NX2_*` and diagnostic switches.
- A game's own switch defaults (below, "Defaults for Ocarina of Time") come between your settings and the shipped file: the real environment wins, then your own `nx2_switches.txt` (the per-user copy, or `user\nx2_switches.txt` in a portable install, or one next to the AppImage), then the game's defaults, then the copy shipped next to the executable. A game's default replaces a value only the shipped copy set; a value you set, to anything, `0` included, stays.
- Your per-user copy also holds two blocks you did not type: the settings page's mode block at the top and the launcher's block at the end, which the launcher rewrites before every start it makes. Who writes each part, and when each file is read or rewritten: [lifecycle.md](lifecycle.md#2-environment-and-switch-files).
- Most switches are read once, at start: restart after a change. Those marked "live" can also be changed in a running game through the debug server (`EDEN_NX2_DEBUG_SERVER`, [nx2/debug-mcp.md](nx2/debug-mcp.md)).
- Unset, or `0`, leaves the emulator as it is without the switch, unless the row says otherwise.
- "Off by default" below is the code's default. A line in the shipped `dist/nx2_switches.txt` turns a switch on in every release package, unless a game's switch defaults replace it (below): read that file to see what a release runs with.

## Status

- **proven**: a measured gain on a verified scene: `tools/bench` rows with `scene_ok: true`, paired with a baseline from the same session. Still off by default until it has been checked on more than the scene it was measured in.
- **experimental**: no verified gain yet, or measured without a gain. "No gain" and "slower" results stay in the row; such a switch is a candidate for removal.
- **diagnostic**: logs, traces, probes and verifiers. They change no output but can cost time, so do not measure performance with them on unless the row says it is cheap.
- **default on**: behaviour Guarana ships on, and the switch that turns it off.

"No verified-scene measurement" means nobody has measured it the way rule 1 of AGENTS.md asks. The measurement setup below, "Arc 140T", is: Core Ultra 9 285H, Intel Arc 140T, driver 32.0.101.9175, plugged in, 1280x765 window, Ocarina of Time, Hyrule Field.

Origin is ours unless the row says otherwise. Paths are under `src/`.

Known issues of `EDEN_NX2_GM`:

- Bit `8` returns zero for an address outside the buffers the compiler names. It was checked in one scene only: if a game renders wrongly with `11`, try `3`, then no switch.
- Bit `4` has no run-time comparison: an address below the pointer's binding reads out of the binding's bounds (robust buffer access, not guaranteed zero) where bit `8` returns zero. Nothing about the pointer's value is baked into the shader, and with bit `4` unset the IR is unchanged. It is not on by default for any game.
- Fixed (issue #105): with bit `2`, a Vertex B program joined to a Vertex A one (`MergeDualVertexPrograms`) kept its narrowed buffer lists in its own descriptor indices, while its storage buffers moved after Vertex A's: a load searched Vertex A's buffer at that index, and with bit `8` read zero. `RemapStorageBindings` now moves the lists with the bindings and drops a list it cannot map (the load then searches every buffer).
- Fixed (public issue #6): with bit `2`, a narrowed load stored its buffer list in its flags (`global_memory_to_storage_buffer_pass.cpp:2610-2629` before the fix), and two readers took those flags for something else. `collect_shader_info_pass.cpp:141` read them as a `bool`, the LDG.CG "coherent" bit, so every program with a narrowed load was marked coherent: its storage buffer blocks got the `Coherent` member decoration (`spirv_emit_context.cpp:317`) and its barriers the coherent memory semantics (`emit_spirv_barriers.cpp:22`; the GLSL and GLASM backends and `emit_spirv_tensor.cpp:37` read the same bit). The other way, `spirv_emit_context.cpp:1029-1034` and `1284-1332` read the whole flags as the list: an LDG.CG load that was not narrowed has flags 1, which names buffer 0 only. That load then read buffer 0 for every address at or above its base, including addresses that belong to another buffer, and sent only the addresses below it to the fallback (zero with bit `8`). The pass also cleared a coherent bit when it could not narrow a load. The flags are now `IR::GlobalLoadFlags` (`shader_recompiler/frontend/ir/modifiers.h`): bit 0 is the coherent bit, bits 1 to 28 the buffer list, and each reader takes only its part. The numbers in the table above were measured before the fix, with the `Coherent` decoration on the foliage mesh program: measure again (plan below) before quoting them. No cache version changed: the Vulkan disk cache holds guest environments, not SPIR-V (`video_core/pipeline_cache_files.h`), and the driver pipeline binaries are only used when the driver's key of the create info, which includes the SPIR-V, equals the stored one (`renderer_vulkan/vk_pipeline_binaries.cpp:258`), so a changed module rebuilds its pipeline by itself.

Measurement plan for the `EDEN_NX2_GM` flags fix (nothing here has been run; it needs two builds, the build before the fix and the build after it):

1. Shader sweep, offline, on the local corpus (native captures and the Ocarina of Time Vulkan cache under `shader/0400486024dec000`; see [tools/nx2/shader-sweep.md](../tools/nx2/shader-sweep.md)). The sweep reads `EDEN_NX2_GM` like the pipeline cache does, so run it with `11` and with it unset, once per build, into four output directories:
   `EDEN_NX2_GM=11 python3 tools/nx2/shader_sweep.py <native dumps> <cache dir> --compiler <build>/shader-sweep --output sweep-<build>-gm11`
   (the second build with `--contexts-from` the first one's `results.json`). Expect: no new failures or `spirv-val` errors; with the variable unset, every module byte-identical between the builds (the fix changes no code without bit `2`); with `11`, only programs that narrow or contain an LDG.CG load differ. In program `3509ed3aadb5171e` (the foliage mesh program) the `OpMemberDecorate ... Coherent` lines on the storage buffer blocks are gone and the narrowed load functions are the same ones as before; a program with an LDG.CG load keeps its `Coherent` decoration, and an LDG.CG load that is not narrowed calls the full-search function, not a function over buffer 0. Diff each pair with `spirv-dis` and list every module that differs, with the reason.
2. In game, image check of Hyrule Field with `EDEN_NX2_GM=11` (also the default), the same save, camera spot and time of day as the 14.8 to 22.8 fps measurement: capture the frame with the build before the fix and after it (frame dump, or the same screenshot key at the same frozen moment), compare them pixel for pixel, and keep the foliage in view. Any difference in the foliage is a failure of the fix. Then fps and p99 frame time over the same 60 s route in both builds, to see what dropping the `Coherent` decoration does to the 22.8 fps figure, and replace the numbers in the table with the new pair. The caches need not be deleted between builds (a changed module fails the driver key check and is rebuilt); delete them only to compare cold shader build times.

## Removed experiments

Switches Guarana added and then removed because a paired run showed no gain, or harm. The code is gone; `git log -S` finds it.

| Switch | What it did | Why removed |
|---|---|---|
| `EDEN_NX2_MESH_SIMD` | Forced the subgroup size (8, 16 or 32) of native task and mesh stages. | No gain beyond the run-to-run spread on the Arc 140T scene (lab rows m-simd8/16/32: 15.4, 15.9, 15.7 fps against 15.9 for j-base). |
| `EDEN_NX2_IGPU_VRAM_MIB` | Replaced the integrated GPU's 4 GiB (6 GiB aggressive) memory share with a size in MiB. | No gain: 15.5 fps with 8192 MiB against 15.1 for the trace baseline (r1-vram8, r1-ours-trace), and no gain from the matching texture-cache threshold raise (v10-tc 21.0 against 19.5 fps). |
| `EDEN_NX2_DEPTH_OPTIMAL` | Kept the depth attachment in DEPTH_STENCIL_ATTACHMENT_OPTIMAL during (mode 2: between) render passes, with the scheduler returning it to GENERAL before other work. | No gain: the bundle with the other attachment experiments ran 15.5 fps against 15.1 (g-half-a, f-plain); the owner's note lists the layout fix as no gain. |
| `EDEN_NX2_RT_USAGE`, `EDEN_NX2_RT_USAGE_SIZE` | Created single-sample colour render target images without STORAGE usage (RT_USAGE_SIZE limited it to one size). | No gain: it ran only inside the g-half-a bundle (15.5 fps against 15.1); it was only measured in that bundle. |
| `EDEN_NX2_ALIAS_LAZY` | Marked a render target modified only when the draw's write masks let it write it, so aliases sampled between such draws were not copied again. | No gain: ran inside the g-half-a bundle (15.5 fps against 15.1); the owner's note lists the alias fix as no gain. The EDEN_NX2_ALIAS_TRACE diagnostic stays. |
| `EDEN_NX2_DEFER_WFI` | Kept the open render pass on wait-for-idle on every driver (as MoltenVK does) and deferred the query sync. | No gain: ran inside the g-half-a bundle (15.5 fps against 15.1); the owner's note lists deferred sync as no gain. |
| `EDEN_NX2_MESH_OUT` | Cheaper native mesh outputs: bit 1 no output for components the fragment stage never reads, 2 a 2x2 primitive shading rate for tiny triangles (EDEN_NX2_MESH_VRS_PX set their size in pixels), 8 one store per output vector, 16 only as many vertices as the primitives use. | Slower or no gain on the Arc 140T scene: bits 8 and 1 ran 13.4 fps (g-out9) and 13.6 with cull 7 against 15 to 16 for the plain runs; bit 16 did nothing (k-count 16.1 fps against 15.9 for j-base) and 16 plus 8 was slower (k-count-vec 14.7 fps). The owner's note lists the output rewrite as no gain. EDEN_NX2_MESH_VRS_PX went with it: it only tuned bit 2. |
| `EDEN_NX2_MESH_CULL` | Native mesh programs culled their triangles: bit 1 outside the frustum, 2 covering no pixel centre, 4 no outputs for a workgroup with no triangle left. | Slower on the Arc 140T scene: 12.2 fps against 14.47 for the baseline (r4-cull1), and 13.6 fps together with MESH_OUT 9 (g-cull7-out9). The owner's note lists mesh culling as no gain. The tools/bench igpu-switches variants went with it. |
